# 1. Purpose

This document converts the v0.1 technical specification into implementation tasks suitable for direct creation as GitHub Issues.

Each task contains:

- issue title;
- objective;
- scope;
- implementation notes;
- expected files/components;
- acceptance criteria;
- tests;
- dependencies;
- suggested labels;
- pull request requirements.

The intent is to provide traceability:

```text
Design
   ↓
GitHub Milestone
   ↓
GitHub Issue
   ↓
Feature Branch
   ↓
Pull Request
   ↓
Review
   ↓
Merge
   ↓
Issue Closed
```

# 4. Pull Request Convention

Each implementation issue should normally result in one pull request.

Branch naming:

```text
feature/<issue-number>-short-description
fix/<issue-number>-short-description
chore/<issue-number>-short-description
```

Example:

```text
feature/12-project-creation
```

Commit messages should remain descriptive.

Example:

```text
Add project creation service
```

The pull request should contain:

```text
Closes #12
```

when it completely resolves Issue 12.

If it only partially contributes:

```text
Related to #12
```

# 12. Pull Request Scope Rule

Prefer:

```text
1 implementation issue
=
1 pull request
```

unless tasks are trivially coupled.

Avoid large pull requests containing:

```text
Electron setup
+
project persistence
+
TipTap
+
autosave
+
PDF export
```

Smaller PRs provide:

```text
better review
simpler rollback
clearer history
better issue traceability
lower merge risk
```
